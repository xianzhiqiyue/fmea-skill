# 前置放大器第五轮验证

## 目的

使用第五个真实模块 `前置放大器` 验证 `openclaw-fmea-cocreator` 在“保护链路 + 低噪声放大 + 控制逻辑”这类模块上的表现，重点看三件事：

1. 自动 `scope` 是否能稳定拆出保护、低噪声放大、控制逻辑三类子系统
2. 是否能保留同一射频前端家族里的高价值类比
3. 是否能压掉只是“沾到接口/供电/串扰”泛词的弱相关噪音

## 验证对象

- 模块名称：`前置放大器`
- FMEA 类型：`DFMEA`
- 验证重点：T/R 保护、LNA、功率检测、模式逻辑、DB-37 控制接口

## 自动 scope 结果

本轮自动识别出了 3 个 scope：

1. `T/R与保护子系统`
2. `低噪声放大与接口子系统`
3. `控制逻辑与供电子系统`

这个拆分是成立的，也符合前置放大器的实际边界。

## 初次试跑发现的问题

第一次试跑时，虽然整体方向是对的，但仍出现了两个问题：

1. `匀场单元` 的 `DB50` 接口案例被拉进了 `低噪声放大与接口子系统`
2. `收发机` 的发射泄漏条目被拉进了 `控制逻辑与供电子系统`

这说明仅靠“模块家族优先”还不够，射频前端家族内部和家族外部需要更细的边界。

## 这轮新增修正

基于这次验证，已经补了两类规则：

1. 显式定义射频前端家族
   - `前置放大器`
   - `收发机`
   - `射频功放`
   - 这些模块之间允许作为直接相关模块参与类比

2. 对相关模块但焦点命中偏弱的条目继续过滤
   - 不是同模块本身
   - 即使属于相关家族
   - 如果在 `analysis_object + function + failure_mode` 上仍然不够像，就不进入草稿

同时，也补全了 `T/R与保护子系统` 的关键词，让：

- `VSWR`
- `驻波`
- `复位`
- `热管理`

这类本就属于保护链路的案例可以更稳定地归到保护 scope。

## 当前结果评价

### 已证明有效的部分

- 自动 scope 能稳定拆出 3 个子系统
- 当前模块样例已经覆盖了前置放大器的主干风险
- 同一射频前端家族的高价值类比能被保留
- `匀场单元` 和其他弱相关模块的噪音已经被压掉

### 当前仍需人工把关的点

1. `T/R与保护子系统` 里保留了多条 `射频功放` 的类比
   - 例如 `保护动作严重滞后`
   - 例如 `VSWR 失配检测`
   - 例如 `热管理系统`
   - 这些在工程上是有参考价值的，但正式版仍应确认是否属于当前前置放大器的责任边界

2. `低噪声放大与接口子系统` 里保留了 `射频功放` 与 `收发机` 的类比
   - `射频功放` 的增益压缩
   - `收发机` 的接收链非线性失真
   - 这些属于“同家族近邻类比”，可以帮助补全思路，但不应直接等价替代正式条目

3. `O/D` 仍需专家确认
   - 尤其是 PIN 热击穿、保护滞后、VSWR 检测误差、接口拉弧、LNA 自激、模式逻辑死锁
   - 这些都强依赖高功测试、屏蔽验证和整机联调能力

## 对 skill 的直接结论

这轮验证让 skill 的检索边界更清楚了：

1. 不只是“当前模块优先”
2. 还要区分“直接相关家族”和“完全无关模块”
3. 同家族类比可以保留，但也要满足焦点字段强匹配
4. 这样既能补位，又不会把草稿拉得过宽

## 下一步建议

下一步最合适的是下面两个方向之一：

1. 做第六个真实模块验证，例如 `射频功放`
